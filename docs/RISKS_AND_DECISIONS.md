# TilSwitch AI risks and decisions

Planning status as of Nov 14, 2026. High, medium and low are planning estimates. Update the owning task and [progress](../PROGRESS.md) when a trigger fires. The [backlog](../TASKS.md) supplies deadlines.

## Assumptions to verify

- One eligible student is available, can approve and run the plan during the official window, and is already registered or otherwise has valid participant access. Verify before relying on a competition submission. Publication route and internet access are implementation checks.
- The developer can spend roughly a long workday plus an evening over the remaining window, can use Python and Git, and can rest as scheduled. Invite help with bilingual review if the team has another eligible contributor.
- At least one fluent Kazakh–Russian speaker can judge colloquial words. Independence and sampling limits will go into the report. If this is untrue, use a narrow mono release and mark mixed behavior exploratory. Human review for English is a smaller secondary requirement.
- Weak monolingual supervision and a neighbor feature can establish a reasonable baseline. Neither accuracy nor a context gain is proven. Tatoeba’s Kazakh row count is enough to try a CPU model, potentially with fewer clean rows than expected.
- KRCS is a useful external register check and likely skewed toward messages with switching. It cannot estimate class prevalence or all student chats. A small authored contrast set provides a separate source of negatives.
- Local Python is available. Pinned-package compatibility, raw-data download speed, installation and runtime resources need an actual clean-environment check during implementation.

## Gates and decisions

| Gate | Go condition | Triggered action |
|---|---|---|
| Entry and availability, T01 | Entrant and usable official route identified. | Check confirmation email and form. Record unavailable routes separately from local feasibility. |
| Mono inventory, T03/T06 | All three configured payloads validate, then ≥500 train and ≥100 dev/test messages per language after gates, with group isolation. | At 30 minutes without valid rows switch to FLORES. If both routes fall below group support, document smaller real counts, avoid three-language claims beyond measured slices and lock the narrowed path before test access. |
| Gold readiness, T05 | At least one bilingual reviewer, test gold frozen before inspection with target minimums and support per label in research plan. | Use separately prepared authored gold if it meets the fallback gate. If absent, preserve independent mono comparison and reduce mixed claims. Report exact missing data. |
| Candidate decision, T08/T09 | C beats W in base dev macro-F1 and retains W's policy Kazakh recall and coverage on matching dev. | If C fails dev gate, has unresolved fit issues or arrives late, ship W. Preserve C measurements that were run. Freeze the mixed-indicator wording with the [authored-dev gate](ML_RESEARCH_PLAN.md#fit-specification). Document actual rates and coverage. |
| Locked evidence, T09/T10 | Source and dedup receipts, independent gold hash, analysis config and actual predictions all match. | Integrity failure blocks the affected results. Publish clean comparable runs only. If no external results are sound, disclose the narrowed scope. |
| Executable release, T12 | Clean test path and CLI work, demo reliably shows actual analysis, artifact/source hashes and privacy pass. | If browser work stalls or fails by Sun 19:05, keep the verified CLI and switch to public notebook if feasible. Never use fixture results as live demo predictions. |
| Publication, T13/T14 | Public code and write-up work signed out, team and credits ready. | Submit that version before demo video. If upload is broken, use the alternate public route and the official support contact. |

The starter sample size and use of a particular language-detection library are implementation suggestions. The planned original contribution is measurable word-level analysis for a student workflow and a reviewed external evaluation, with the context model opt-in by evidence. Acceptance gates above are the team's engineering decisions. Competition conditions are tracked in [submission requirements](HACKATHON_SUBMISSION.md).
